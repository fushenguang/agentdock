# design · cli-publish-giturl-scope

## 唯一真正需要裁决的一处：老版本 CLI 不发 `path` 时怎么办

`≤0.12.0` 已经发到 npm 上，用户手里就有。它们发的请求里没有 `path`。服务端拿到一个仓库根 URL 时有三种可能行为：

| | 行为 | 好 | 坏 |
|---|---|---|---|
| **A（倾向）** | **拒绝**，返回明确错误，提示升级 CLI | 不变量从此刻起成立，registry 里不会再出现粗粒度行 | 老版本用户的 publish 会失败——但**失败得很吵**（有明确错误信息和升级指引），比静默落一行会导致付费绕过的数据好 |
| B | 服务端自己 clone 仓库、扫出唯一的 SKILL.md 再推断子路径 | 老版本无感 | 服务端要具备拉取能力（这正是方案 C 当初刻意避开的工作量）；且仓库有多个 skill 时推断不出来，还是得拒绝 |
| C | 放行但标记 | 最省事 | **等于把洞留着**，只是加了个标签。与「诚实标注」不同——标注是给人看的信息，这里是一个可被利用的授权面 |

**倾向 A。** 理由：这是一个**授权面**问题，不是体验问题。写入侧宁可吵闹地失败，也不要静默落下一行会在别处变成绕过的数据。且 CLI 刚发 0.12.0、真实用户基数极小（目前只有构建者自己），这是收口不变量成本最低的时刻。

⚠️ 选 A 需要同刀做的事：CLI 侧的错误信息必须**可执行**——明确说「升级到 `>=0.13.0`」而不是抛一个 HTTP 400。

## 拼装放服务端而不是客户端

客户端拼好完整 URL 再发，看起来更省事，但那意味着**registry 的数据形状由客户端决定**——和「客户端自报扫描结果」是同一类错误。服务端收原料（`git_url` + 分支 + `path`）自己拼，形状的责任才在服务端。

## 「拒绝粗粒度 URL」的判据怎么写

不要用「URL 里有没有 `/tree/`」这种字符串特征——太脆。判据应当是**语义的**：解析结果必须能定位到**恰好一个** skill（即该路径下有且只有一个 `SKILL.md`）。

本刀不做服务端 clone（Non-Goal），所以服务端**无法直接验证**这一点。可行的近似：要求请求同时提供 `path` 且 `path` 非空，把「这一个 path 指向一个 skill」这件事交给 CLI 保证（CLI 本来就是按单个 skill 目录发布的，`skill publish <dir>` 的 `<dir>` 就是那一个 skill）。这是**结构性保证而非校验**——比事后校验更可靠，因为 CLI 根本没有能力发出一个"指向多个 skill 的 path"。

## 第 4 条（electron 只装匹配的目录）为什么独立成条

它不依赖前三条中的任何一条，也不被它们取代：

- 前三条管住的是**我们自己的 registry**里的数据
- 第 4 条管住的是**下载到本地之后的行为**——包括将来 registry 数据又出问题、或者引入第三方 registry 的情况

注意**不要**顺手改「粘 git URL 手动安装」那条路径：它没有 `skill_id`，本就没有可匹配的对象，且那条路径明确没有授权门（用户自己粘的 URL，自己负责）。
